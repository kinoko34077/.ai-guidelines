# Refactoring & Optimization Standard
## 既存実装の改善・リファクタリング・最適化 専門標準

- **状態:** 草案 v0.1（未承認・未正本化）
- **作成日:** 2026-11-01
- **想定配置:** `GPT共有用／情報源／開発・仕様／Refactoring_and_Optimization_Standard.md`
- **性質:** 開発分野の専門的な Domain Source（既存 Core Source を置換しない）
- **対象:** プログラム、Web アプリ、デスクトップアプリ、プラグイン、API、ライブラリ、CLI、ゲーム、データ処理系、DSP 等の既存実装

> **草案の扱い:** 以下は今回の要望を具体化するための「提案規則」であり、既存資料にすでに確定記載された規則と区別する。承認・正本化されるまでは既存の開発原則や個別仕様へ自動適用しない。記載の数値例・技法は、個別案件の性能目標や技術選定を確定するものではない。

# 第 I 部　適用条件・守るべき契約

## 第0章　文書の位置付け

### 0.1 目的

本書は、既存実装に対する軽量化・効率化・高速化・構造改善（責務分離、平易明瞭化、共通化等）について、**診断、改善候補の選択、変更実行、既存契約の保持、効果の実証、終了判断**を一貫して運用するための専門標準を定める。

本書は、ソースコードの短縮、抽象化の増加、最新ライブラリへの置換、ファイル細分化などを、それ自体で改善とみなさない。改善が成立したと判定するには、対象問題への作用と、変更後の証拠を要する。

### 0.2 上位正本との関係

以下の既存資料を優先して参照する。

- `03_Development_Specification_Principles.md`: 要求・実装の分離、責務の変更理由、知識の一元化、互換性、検証、巻き戻し、AI 開発、作業進捗の耐久化。
- `05_Project_Knowledge_Governance.md`: Core / Domain / Current State / Work Artifacts の配置、正本の重複・陳腐化の防止。
- `プログラム仕様管理・運用指示書.txt` および `仕様書化・仕様管理 指示マニュアル.txt`: 仕様 ID、変更理由、影響範囲、仕様・実装・テスト・履歴の対応付け。
- `04_Research_Evidence_Standard.md`: 外部技術情報の確認、主張と証拠、時点・環境差の管理。

本書ではこれらの一般原則を再定義せず、**既存コードの改善に固有の実行・判定条件**を追加する。具体的な性能予算、対応環境、保存契約、互換性、優先度、検証結果は対象案件の正本・Issue 等で定める。衝突時の優先順位は Project Instructions と既存正本に従う。

### 0.3 適用契機と範囲

明示的な改善依頼のほか、既存機能の改修・障害修正・性能問題・重複実装の発見時にも、関連箇所への適用を検討する。ただし、**調査対象を常に全コードベースへ拡張することは要求しない**。影響が広域に及ぶ兆候がある場合に調査範囲を拡大する。

4領域はいずれも診断対象となるが、全領域で実際に変更を行う義務はない。問題がない、効果が小さい、リスクが高い、検証不能である等の場合は「変更しない」を正当な判定として扱う。

## 第1章　改善活動の分類と目的

### 1.1 作業種別の区別

| 種別 | 主目的 | 意図的な外部挙動の変更 | 必要な判定 |
|---|---|---|---|
| 厳密なリファクタリング | 内部構造の改善 | 原則として行わない | 契約保持＋構造改善 |
| 性能・資源最適化 | 実行・資源特性の改善 | 機能上の契約を保持し、品質特性を改善 | 契約保持＋性能・資源比較 |
| 不具合修正 | 仕様と実態の不一致を解消 | 必要に応じて変更する | 期待仕様・再現条件・回帰 |
| 機能・仕様変更 | 許容される振る舞いを変更する | 行う | 新仕様の受入条件・互換性 |
| 環境更新・移行 | 依存・基盤・環境の更新 | 意図しない変更は防ぐ | 移行契約・互換性・運用検証 |

これらが一つの作業の中で関係しても、目的・差分・証拠を区別する。機能変更を「リファクタリング」と呼んで契約変更の確認を省略しない。単純な局所変更を除き、構造変更と意味変更を独立検証可能な差分に分けることを基本とする。

### 1.2 4つの改善領域

| ID | 領域 | 主な削減・向上対象 | 判定上の注意 |
|---|---|---|---|
| L | 軽量化 | メモリ、ストレージ、通信量、配布物、無駄な資源消費 | ソース行数は直接の成果指標ではない |
| E | 効率化 | 計算量、処理回数、データ移動、I/O、作業量 | 部分的な高速化と全体の仕事量削減を区別する |
| P | 高速化 | 遅延、起動・処理時間、スループット、期限内処理 | 比較可能な実測と負荷条件が必要 |
| S | 構造改善 | 変更波及、責務混在、結合、知識重複、理解・検証負担 | ファイル数・クラス数・抽象層数の増減のみで判断しない |

**改善の成立条件:** 指定した領域で検証可能な便益を示し、同時に守るべき契約と他領域の許容条件を満たすこと。領域間の相殺を隠さず、改善の根拠を個別に示す。

## 第2章　不変条件・品質予算・変更の禁止境界

### 2.1 変更前に確認する契約

影響範囲に応じて、次を確認し不変条件（または明示的変更対象）として識別する。

- 入力、出力、エラーの種類と優先順位、境界値、丸め、数値精度、時刻・順序、非決定性の許容範囲。
- 既存 UI の操作・表示・アクセシビリティ、Undo/Redo、保存・復元、ユーザーデータ、公開 API / CLI、シリアライズ形式。
- 状態遷移、非同期処理、並行性、リアルタイム期限、セキュリティ、権限、プライバシー、ライセンス、配布条件。
- 対応 OS・ブラウザ・端末、低速環境、旧版データ、外部連携、オフライン動作等の個別契約。

既存のコードが示す観測挙動と、現在有効な仕様を同一視しない。既知の不具合・未確定挙動・仕様矛盾は区別し、必要なら別の不具合修正・仕様変更として扱う。

### 2.2 品質の非退行

主目的ではない領域も、影響の大きさに応じて監視する。速度が上がってもメモリが予算超過になる、コードが単純になっても保存互換を壊す、といった変更を無条件に採用しない。

**許容される差異は案件ごとに定義**する。浮動小数点演算の許容誤差、音響処理の客観的な音質指標、フレーム期限、API レイテンシ、UI の操作感などへ、全案件共通の数値を押し付けない。

### 2.3 禁止・停止条件

次に該当する場合、修正・検証または明示的な判断が成立するまで、対象差分を「改善完了」としない。

1. 既存の確定契約に反することが判明した。
2. 性能・資源などの重要な品質が、定めた許容範囲を超えて悪化した。
3. 作業によって安全性・権限境界・データ整合性を侵害する疑いがあり、検証できない。
4. 機能・仕様の意味変更が必要なのに、対象の変更契約が未確定である。
5. 効果の主張に必要な測定・比較がなく、実証済みであるかのように報告しようとしている。

測定できない事情そのものは、調査・低リスクの構造改善を全面禁止する理由ではない。ただし、**未測定の改善効果を実証済みとみなしてはならない**。

# 第 II 部　診断と対象選定

## 第3章　現行実装の分析・問題検出

### 3.1 現状調査の基本単位

現行リビジョン、関連仕様・Issue、実利用の処理経路、関連テスト、依存グラフ、性能基準値を確認する。解析対象は、利用者要求や観測問題と関係する実際の経路を優先する。表示上の呼び出し先と、実行時に使用される実装が異なる可能性にも注意する。

### 3.2 診断内容

| 領域 | 問題の兆候 | 確認手段の例 |
|---|---|---|
| L | 大量割当、メモリ増加、重複データ、過大バンドル | ヒープ追跡、資源計測、依存・成果物解析 |
| E | 不要ループ、重複計算、N+1 I/O、無駄な変換・転送 | トレース、クエリ計画、計算量分析、呼び出し回数 |
| P | 遅い起動、遅延の偏り、長いブロッキング、処理落ち | プロファイラ、負荷試験、フレーム追跡、p50/p95/p99 |
| S | 変更箇所の広域化、循環依存、責務混在、知識重複 | 依存グラフ、変更履歴、仕様追跡、変更シナリオ試験 |

### 3.3 証拠区分

問題候補には少なくとも次を区別して記録する。

- **観測事実:** 対象リビジョンと条件付きで実際に取得した数値・ログ・挙動。
- **解析による所見:** 静的解析、計算量・依存分析などから導いた構造的判断。
- **仮説:** 原因や改善可能性が未検証の説明候補。
- **未確認:** 必要な環境・データ・権限がなく、判定不能な項目。

警告数や「コードの臭い」の検出数を、実害や改善優先度へ直接変換しない。実害・変更頻度・仕様上の重要性へ対応付ける。

### 3.4 基準値の取得

改善前の計測値は、対象コミット、OS・ランタイム・ビルドモード・端末、入力データ、負荷・同時実行数、ウォームアップ、キャッシュ状態、試行回数、指標と単位を記録する。比較可能な測定を組めない場合は「基準値未取得」と明記し、先に計測環境の整備を検討する。

## 第4章　改善候補の評価・優先順位

### 4.1 候補ごとの判定項目

候補は「原因 → 変更手段 → 期待される効果 → 影響範囲 → 検証方法」の対応で記述する。少なくとも次を比較する。

- 利用者・運用・開発上の損失の大きさと発生頻度。
- 直接の改善効果（測定可能な場合は推定幅と根拠）。
- 契約・互換性・安全性・品質予算へのリスク。
- 実装、計測、レビュー、移行、保守の総コスト。
- 独立して変更・検証・復旧できる範囲。
- 放置した場合の損失と、他作業の前提になる度合い。

### 4.2 優先判断

セキュリティ・データ破損等の既存の高優先度問題は、単なる見通しの悪さより優先され得る。ただし本書は新たな一律優先度表を作らず、案件の目標・リスク・既存の開発運用上の優先順位に従う。

改善候補は、**実行 / 先に計測 / 先に仕様確定 / 別Issueへ分離 / 保留 / 不採用**のいずれかへ分類する。低価値な項目を発見しただけで実装タスクへ自動昇格させない。

### 4.3 停止を含む最適化

明確な価値がない改変、測定誤差以下の便益、検証費用に見合わない候補、ほかの品質へ過大な副作用をもたらす候補は実行しない。改善候補の数・修正ファイル数・行数削減量を成果指標としない。

# 第 III 部　改善手段と適用条件

## 第5章　軽量化（L）

### 5.1 目的と主要指標

同等の要求を満たすために消費する資源を減らす。代表指標は、常駐メモリ、ピークメモリ、アロケーション量、配布サイズ、ディスク使用量、データ転送量、CPU 稼働量、電力消費等である。測るべき指標は対象システムの制約から選定する。

### 5.2 改善候補

- **所有・寿命の整理:** 不要に保持するデータ、リーク、解放遅延、複数層での同一情報保持を減らす。
- **割当とコピー:** 高頻度の短命オブジェクト、不要な中間配列、直列化・複製を減らす。
- **読み込み範囲:** 不要なアセット・モジュール、未使用コード、不要な機能同梱を削減する。
- **データ構造:** サイズ・アクセス特性・更新頻度に応じた表現へ切り替える。
- **キャッシュとバッファ:** 過大保持・多重キャッシュを抑え、必要な寿命と容量を設定する。
- **依存整理:** 重複・未使用依存を確認し、代替実装の保守コストを含めて廃止可否を判断する。

### 5.3 除外と副作用

データ圧縮は展開時間・CPU負荷を増やし、遅延読み込みは初回待機を増やし得る。メモリ節約のための再計算は高速化に反する場合がある。依存削除に伴いセキュリティ更新・互換処理を独自実装するなら、逆に総保守負担が増える可能性がある。

**採用条件:** 選んだ資源指標が比較可能な条件で改善し、規定された応答・安定性・互換性を損なわない。

## 第6章　効率化（E）

### 6.1 目的

必要な結果へ到達するまでの**仕事量そのもの**を減らす。実行時間だけではなく、計算回数、走査量、I/O回数、転送量、再描画回数、ビルド・テスト等の作業量も対象とする。ただし開発工数の削減は実行効率と分けて記録する。

### 6.2 優先する診断順

1. 不要な処理がそもそも発生していないか。
2. 同じ結果を複数箇所・複数回生成していないか。
3. 対象データを必要以上に走査・転送・コピーしていないか。
4. アルゴリズムとデータ構造が実際の入力規模に適しているか。
5. 必要な処理を、適切なバッチ化・遅延処理・差分更新にできるか。

### 6.3 代表手段と適用境界

検索索引、適切なキャッシュ、バッチ I/O、差分更新、クエリ最適化、計算結果の再利用、ベクトル化、処理順序の変更、データ局所性の改善などを候補とする。採用に際しては、最新性、処理順序、並行性、例外、無効化条件、メモリ・同期コストを確認する。

**禁止される短絡:** 「ループを減らしたから効率的」「非同期・並列にしたから効率的」「キャッシュを増やしたから速い」と、実行経路や仕事量を確認せず断定しない。

## 第7章　高速化（P）

### 7.1 計測を先行する

高速化は、利用者または処理要件に対応する指標を定義した後に実行する。平均だけでなく、対象に応じて中央値、p95、p99、最大値、フレーム期限超過率、スループット、起動時間等を用いる。入力規模や混雑条件が異なる結果をそのまま比較しない。

### 7.2 ボトルネックの選定

CPU・メモリ・GPU・I/O・待機・ロック競合・ネットワーク・DB・UI描画など、遅延の原因を区別する。全処理の小部分にしか寄与しない箇所の最適化は、全体への改善上限を見積もってから着手する（Amdahl の法則）。

プロファイラで得た呼び出し数や累積時間と、独立したベンチマークで得た全体実行時間は用途が違う。計測器のオーバーヘッドを考慮し、比較には適したベンチマークを用いる。

### 7.3 手法の選択

アルゴリズム・処理回数・データ移動の改善を先に検討し、その後に対象経路の演算最適化、バッファリング、並列化、SIMD、キャッシュ局所性、レンダリング最適化等を選ぶ。ただしハードリアルタイム等では局所最適化が必須となることもある。

### 7.4 比較・判定

Before / After を同じ環境・入力・測定条件で繰り返し測定する。必要に応じて測定順序を交互にし、ノイズやウォームアップの影響を調べる。観測差がばらつきに埋もれる場合は「改善未立証」とし、明確な効果を示すまでは数値の誇張をしない。

数値精度・消費メモリ・電力・フリーズ頻度が速度とトレードオフになる場合は、当該予算との整合を別に検証する。

## 第8章　構造改善・責務分離・平易明瞭化（S）

### 8.1 目的

理解・修正・拡張・検証に必要な作業を減らし、変更理由が無関係な箇所へ波及しない構造へ近づける。既存 Core Source にある「変更理由による分離」「同一知識の一元化」「情報隠蔽」を具体的な診断と移行へ変換する。

### 8.2 診断単位

- **変更理由:** 何が変わるとその要素を修正するか。異なる変更理由が同一モジュールへ混入していないか。
- **情報の所有:** 同じルール・定数・変換規則が複数箇所で独立管理されていないか。
- **依存の方向:** 変更頻度の高い詳細へ上位機能が過度に依存していないか。循環依存が生じていないか。
- **状態の境界:** 誰が生成・更新・破棄するかが明確か。同期・不変条件が隠れていないか。
- **公開契約:** 実装都合を過剰に公開していないか。インターフェースの利用者を特定できるか。
- **可読・変更コスト:** 実際の変更シナリオで修正箇所・必要知識・テスト範囲が減るか。

### 8.3 共通化・再利用

類似コードを機械的に一つにしない。**同一の知識・仕様・変更理由を共有する**場合に共通化候補とする。似ていても異なる仕様・独立した変更理由を持つ場合は、共通化による条件分岐・結合の増大を比較する。

同等機能が既に提供されている場合は、現行正本・公開 API・バージョン・依存関係・互換性を確認してから再利用を優先する。特に repository を跨ぐ共通モジュールは、所有者、変更手続、互換方針、利用側の検証経路を定義する。単に「共通 API がある」という理由だけで移行を完了したとみなさない。

### 8.4 過剰分割・過剰抽象化の抑制

モジュール数・層数を増やせば責務分離したことになるわけではない。細分化によって依存を追う回数、インターフェースの数、実装を理解するための移動量が増える場合、統合した方が平易になる可能性がある。変化が確認されていない将来想定のために汎用フレームワークを導入しない。

### 8.5 削除と廃止

不要に見えるコードでも、旧データ互換、外部呼び出し、ビルド・運用経路、フォールバック、テスト専用機能として使用される可能性がある。参照探索・実行経路確認・互換確認を経て削除する。移行途中の旧実装・フラグ・アダプタは期限または撤去条件を明示し、永久的な二重管理へしない。

### 8.6 構造改善の実証

静的指標（循環依存、モジュール間の接続、重複知識の減少等）は補助証拠とする。可能なら「同種の機能変更なら何箇所を触るか」「一つの規則変更をどこだけで完結できるか」等の具体的な変更シナリオで、理解・変更・テストの負担を比較する。

## 第9章　複数領域の相互作用・全体判断

### 9.1 独立指標と制約指標

対象の改善指標と、悪化を抑制する制約指標を分離する。たとえばキャッシュは P を改善しても L や S を悪化させる場合がある。抽象層の追加は S を改善しても P を損なう場合がある。縮小した配布物が初回起動を遅くする場合もある。

### 9.2 判断手順

まず契約・安全条件を守る。次に、対象目的に対する実測・実証の便益を比較する。複数候補間で優劣が一意に決まらない場合は、利用条件・運用コスト・変更頻度・後戻りの容易さを比較し、採否理由を記録する。

4領域を単純に足し合わせた「総合点」や、共通根拠のない固定重みは使用しない。**1領域の改善を他領域の重大な悪化で相殺して承認しない**。案件の目的が許容するトレードオフのみ採用する。

# 第 IV 部　変更実行・検証

## 第10章　実行単位・段階的移行・統合

### 10.1 作業単位

可能な限り、一つの差分で一つの改善仮説と検証条件を明確にする。無関係な修正を同時に含めない。変更を小分けにすること自体が目的ではなく、**独立して理解・検証・統合・復旧できる単位**を選ぶ。小さく分けすぎて中間状態が壊れたり意味が読めなくなったりする場合は、機能的に完結した単位へまとめる。

### 10.2 大規模な置換

影響範囲が広く、一度に置換すると比較・復旧が困難な場合は、抽象層や切替機構を用いた段階移行を検討する。旧・新実装の同時動作、差分比較、利用先の順次移行、旧機構の撤去条件を設計する。ただし、これらの移行機構の導入・保持コストを上回る効果が必要であり、小規模修正へ一律導入しない。

### 10.3 実装の進め方

1. 変更前契約・影響・基準値・受入条件を確定する。
2. 必要なら回帰テスト・基準測定を追加して既存挙動を保護する。
3. 変更単位ごとに実装し、その単位で成立する検証を実施する。
4. 対象経路の実稼働確認と必要な広域回帰を実施する。
5. 受入条件を満たした変更のみ、既存の権限・レビュー・CI規則に従って統合する。
6. 自らの変更で生じた参照・仕様・テスト・進捗記録の不整合を修正する。

### 10.4 巻き戻しと変更競合

大規模・互換リスクのある変更では、復旧手段と旧データ・旧設定の可逆性を先に確認する。共有ブランチの強制変更、破壊的マイグレーション、公開・デプロイ等は既存の Human gate を適用する。並行作業中の他者所有範囲へ無断で衝突する変更を行わない。

## 第11章　検証・評価・受入ゲート

### 11.1 3ゲート

| ゲート | 問い | 判定証拠 | 不合格時 |
|---|---|---|---|
| G1 契約保持 | 守るべき外部挙動・データ・互換条件を保ったか | 仕様対応テスト、境界・統合・実稼働経路での検証 | 修正または意味変更として分離 |
| G2 品質非退行 | 対象外の品質が許容値を超えて悪化していないか | 性能・資源・安定性・安全性・運用の回帰 | 修正・撤回・許容差再検討（勝手に緩和しない） |
| G3 目的達成 | 狙った改善が観測・実証されたか | 同条件 Before/After、構造変更シナリオ、依存差分 | 効果未立証・保留・撤回・別候補の検討 |

G1/G2 は対象に応じて適切な範囲を定義する。G3 は目的に対応する指標ごとに判定する。数値で直接測れない構造改善も、具体的な変更波及・責務・依存・保守シナリオを根拠として明示する。

### 11.2 テストが存在しない場合

テスト不足を理由に無制限な書き換えへ進まない。必要なら既存動作を記録する characterization test、仕様から導く境界テスト、差分実行・比較試験を準備する。**観測した既存の不具合を、正しい契約として恒久化しない。**

### 11.3 計測の一貫性

比較時は測定対象・単位・環境・サンプル・負荷・計測モード・キャッシュ・ウォームアップを揃え、変更前後の結果、測定ばらつき、未評価の条件を残す。実環境に依存する性能を、コード読解やスクリーンショットだけで実証したとみなさない。

**時間短縮率の例:** `(T_before - T_after) / T_before × 100%`。これは測定条件が等しく、時間が短いほどよい対象へ適用する。メモリ、スループット、品質指標等を同式で一律に評価しない。

### 11.4 テスト品質

既存テストが通過しても、重要な不変条件が未検証なら G1 の完全な根拠にならない。必要に応じてテストデータの代表性、境界、異常系、実利用経路、変異テスト等を確認する。網羅率だけで欠陥検出能力を保証済みとみなさない。

### 11.5 判定状態

結果は少なくとも、`採用可能` / `改善は確認したが追加検証が必要` / `改善未立証` / `契約・品質違反` / `検証環境不足` に区分する。検証未了を合格に置き換えない。影響のない未検証項目については、範囲と理由を明示して限定受入の是非を判断する。

# 第 V 部　AIによる実行・運用

## 第12章　AIエージェントの実行規則・大局判断

### 12.1 依頼の解釈

「軽量化・効率化・高速化・責務分離を進める」という依頼は、**4領域の問題発見・評価を行い、効果が見込める変更を順次実施する**ことを意味し、必ず各領域にコード差分を作ることではない。指定されていない機能を追加したり、従前仕様を一般的ベストプラクティスで置換したりしない。

### 12.2 AIが記録する最低情報

- 対象案件・リビジョン、上位目標、適用する仕様と権限境界。
- L/E/P/S の各領域で発見した候補または「未検出／未確認」の理由。
- 取り組む候補、問題と原因の証拠、期待効果、別案、変更影響。
- 改善前基準値、G1/G2/G3 の受入条件、実測結果と証拠の所在。
- 作業状態、次の実行単位、blocker、戻し方、未完了条件。

既存の devflow / Repository Control / Issue / PR 等の正式な記録面を使用し、本資料のためだけに競合する新たな進捗台帳を増設しない。現在のリポジトリ状態は live で確認する。

### 12.3 実行ループ

`上位目的確認 → 現状・契約確認 → 4領域の範囲付き診断 → 候補評価 → 変更単位決定 → 改修 → G1/G2/G3検証 → 記録面整合 → 大局判断`

大局判断の結果には `続行`、`経路変更`、`別Issueへ分離`、`保留`、`終了` を含める。目的と受入条件が満たされた場合、関連性だけを理由とする追加修正を開始しない。未達条件が存在する場合も、毎回同じ診断を最初からやり直さず、状態変化と未完了部分を重点確認する。

### 12.4 エージェントの自律範囲

既存の開発原則・権限・レビュー・CI・安全ゲートに従い、承認済み範囲での調査、テスト追加、低リスク変更、PR作成、条件を満たす安全な統合を遂行できる。本書単独で新たな release/deploy、権限変更、credential 操作、破壊操作、公開を許可しない。

### 12.5 終了判定

案件の完了には、(a) 対象範囲と改善目的が明示されている、(b) 受入ゲートの判定と証拠が記録されている、(c) 未完了・保留・非対象が区別されている、(d) 必要な統合・復旧・記録面整合が完了していることを要する。4領域に変更差分が均等に存在する必要はない。

# 付録 E　用語

- **リファクタリング:** 外部の契約上の振る舞いを維持しながら内部構造を改善すること。
- **最適化:** 特定の制約・評価指標に対して、性能や資源効率などを改善すること。
- **不変条件:** 作業の前後で保持することを要求された性質。
- **非退行:** 変更対象外の品質や既存機能が、許容条件を超えて悪化していないこと。
- **プロファイリング:** 処理負荷・時間・資源消費の分布を計測して分析すること。
- **Characterization test:** 既存実装の観測挙動を記録し、意図しない変更の検出に用いるテスト。
- **Mutation testing:** 人工的な欠陥に対するテストの検出能力を調べる手法。
- **p95 / p99:** 値の95% / 99%がその値以下になる分位点。
- **ADR:** 設計判断の理由・代替案・再検討条件等を記録する文書。
