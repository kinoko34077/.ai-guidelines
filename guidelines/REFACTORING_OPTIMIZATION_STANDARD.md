# 第 I 部　適用条件・守るべき契約

## 第0章　文書の位置付け

### 0.1 目的

本書は、既存実装に対する軽量化・効率化・高速化・構造改善（責務分離、平易明瞭化、共通化等）について、**診断、改善候補の選択、変更実行、既存契約の保持、効果の実証、終了判断**を一貫して運用するための専門標準を定める。

本書は、ソースコードの短縮、抽象化の増加、最新ライブラリへの置換、ファイル細分化などを、それ自体で改善とみなさない。改善が成立したと判定するには、対象問題への作用と、変更後の証拠を要する。

**基本判断:** 「対象に固有の目的と制約を保持しつつ、実際の損失を減らせる変更のみ採用する」。修正箇所数、改善候補数、ツールの警告数、文書・テスト数自体を達成目標にしない。

### 0.2 上位正本との関係

以下の既存資料を優先して参照する。Google Drive上の非公開資料は本文を本公開リポジトリへ複製せず、権限のある環境で原本を取得する。アクセスできない場合は未読と明記し、確認済みとして扱わない。参照先は [devflow #734](https://github.com/kinoko34077/devflow/issues/734) を入口として辿る。

- `03_Development_Specification_Principles.md`: 要求・実装の分離、責務の変更理由、知識の一元化、互換性、検証、巻き戻し、AI 開発、作業進捗の耐久化。
- `05_Project_Knowledge_Governance.md`: Core / Domain / Current State / Work Artifacts の配置、正本の重複・陳腐化の防止。
- `プログラム仕様管理・運用指示書.txt` および `仕様書化・仕様管理 指示マニュアル.txt`: 仕様 ID、変更理由、影響範囲、仕様・実装・テスト・履歴の対応付け。
- `04_Research_Evidence_Standard.md`: 外部技術情報の確認、主張と証拠、時点・環境差の管理。

本書ではこれらの一般原則を再定義せず、**既存コードの改善に固有の実行・判定条件**を追加する。具体的な性能予算、対応環境、保存契約、互換性、優先度、検証結果は対象案件の正本・Issue 等で定める。衝突時の優先順位は Project Instructions と既存正本に従う。

GitHubのmanaged repositoryで実作業を行う場合は、live `kinoko34077/devflow/AGENTS.md` → `devflow#734` → 対象のopen Repository Control → Canonical Entry Points → owning Issue/Work Order・仕様・code・testsという既存の参照順序を守る。本書は独自のタスク配車、権限、PR Review、CI、merge、release/deployの基盤を設置しない。進捗は既存のIssue/PR等に残し、個人・機密情報をpublic GitHubへ転載しない。

既存同等機能の再利用については、`devflow/docs/operations/CAPABILITY_REUSE_POLICY.md` および #758 を直接適用する。本書第8章はその置換でなく、改善時の診断・移行・効果判定を具体化する。

### 0.3 適用契機と範囲

明示的な改善依頼のほか、既存機能の改修・障害修正・性能問題・重複実装の発見時にも、関連箇所への適用を検討する。ただし、**調査対象を常に全コードベースへ拡張することは要求しない**。影響が広域に及ぶ兆候がある場合に調査範囲を拡大する。

4領域はいずれも**検討対象**となるが、全領域の詳細診断やコード変更を常に義務付けるものではない。問題がない、効果が小さい、リスクが高い、検証不能である等の場合は「変更しない」を正当な判定として扱う。

### 0.4 診断深度を三段階に分ける

| 深度 | 適用契機 | 実施内容 | 出口 |
|---|---|---|---|
| D0: 影響確認 | 通常の局所修正、明確に限定された変更 | 関係するL/E/P/Sの悪化兆候・既存共通機構・契約を短く確認 | 追加調査が不要なら通常作業へ戻る |
| D1: 対象診断 | 改善の明示依頼、実測した問題、構造上の具体的兆候 | 関連処理経路の4領域を確認し、問題・原因・優先度と証拠不足を識別 | 改善候補を採否または計測待ちに分類 |
| D2: 広域診断 | 複数機能へ同種問題が波及、システム全体の改善依頼、根本原因が局所で特定できない | 依存・性能・資源・変更波及を必要範囲で広く分析 | 範囲と理由を明示して候補を整理 |

D0を実施しただけで「4領域を網羅監査済み」と主張しない。D2を単なる安心感や汎用的な品質向上のために自動実行しない。診断深度の昇格には観測された問題、具体的な影響、または明示要求を要する。

**D0は独立した追加工程ではない。** 通常の実装前の仕様・影響確認に、関連する資源・処理・性能・構造上の悪化兆候を織り込むことを指す。明確な問題がなく、当該変更に関係しない領域の詳細記録や計測を新規に要求しない。

**深度の区分は作業の危険度・review Tierとは別軸**である。D0であっても危険な変更には必要な安全ゲートを適用し、D2であっても調査がread-onlyならそれだけで破壊的変更の許可を生じさせない。

## 第1章　改善活動の分類と目的

### 1.1 作業種別の区別

| 種別 | 主目的 | 意図的な外部挙動の変更 | 必要な判定 |
|---|---|---|---|
| 厳密なリファクタリング | 内部構造の改善 | 原則として行わない | 契約保持＋構造改善 |
| 性能・資源最適化 | 実行・資源特性の改善 | 機能上の契約を保持し、品質特性を改善 | 契約保持＋性能・資源比較 |
| 不具合修正 | 仕様と実態の不一致を解消 | 必要に応じて変更する | 期待仕様・再現条件・回帰 |
| 機能・仕様変更 | 許容される振る舞いを変更する | 行う | 新仕様の受入条件・互換性 |
| 環境更新・移行 | 依存・基盤・環境の更新 | 意図しない変更は防ぐ | 移行契約・互換性・運用検証 |

これらが一つの作業の中で関係しても、目的・差分・証拠を区別する。機能変更を「リファクタリング」と呼んで契約変更の確認を省略しない。単純な局所変更を除き、構造変更と意味変更を独立検証可能な差分に分けることを基本とする。

「構造変更」は**定義された契約上の**観測される挙動の保持を目指す活動であり、「最適化」は主として性能・資源特性の改善を目指す活動である。同一の変換が両方に寄与することはあるが、成功判定は別に行う。なお、構造改善の成果について、数値に還元できない部分があることを認める。ただし「読みやすくなった」という自己申告のみでは十分な証拠にならない。

### 1.2 4つの改善領域

| ID | 領域 | 主な削減・向上対象 | 判定上の注意 |
|---|---|---|---|
| L | 軽量化 | メモリ、ストレージ、通信量、配布物、無駄な資源消費 | ソース行数は直接の成果指標ではない |
| E | 効率化 | 計算量、処理回数、データ移動、I/O、作業量 | 部分的な高速化と全体の仕事量削減を区別する |
| P | 高速化 | 遅延、起動・処理時間、スループット、期限内処理 | 比較可能な実測と負荷条件が必要 |
| S | 構造改善 | 変更波及、責務混在、結合、知識重複、理解・検証負担 | ファイル数・クラス数・抽象層数の増減のみで判断しない |

**改善の成立条件:** 指定した領域で検証可能な便益を示し、同時に守るべき契約と他領域の許容条件を満たすこと。領域間の相殺を隠さず、改善の根拠を個別に示す。

## 第2章　不変条件・品質予算・変更の禁止境界

### 2.1 変更前に確認する契約

影響範囲に応じて、次を確認し不変条件（または明示的変更対象）として識別する。

- 入力、出力、エラーの種類と優先順位、境界値、丸め、数値精度、時刻・順序、非決定性の許容範囲。
- 既存 UI の操作・表示・アクセシビリティ、Undo/Redo、保存・復元、ユーザーデータ、公開 API / CLI、シリアライズ形式。
- 状態遷移、非同期処理、並行性、リアルタイム期限、セキュリティ、権限、プライバシー、ライセンス、配布条件。
- 対応 OS・ブラウザ・端末、低速環境、旧版データ、外部連携、オフライン動作等の個別契約。

既存のコードが示す観測挙動と、現在有効な仕様を同一視しない。既知の不具合・未確定挙動・仕様矛盾は区別し、必要なら別の不具合修正・仕様変更として扱う。

### 2.2 品質の非退行

主目的ではない領域も、影響の大きさに応じて監視する。速度が上がってもメモリが予算超過になる、コードが単純になっても保存互換を壊す、といった変更を無条件に採用しない。

**許容される差異は案件ごとに定義**する。浮動小数点演算の許容誤差、音響処理の客観的な音質指標、フレーム期限、API レイテンシ、UI の操作感などへ、全案件共通の数値を押し付けない。

### 2.3 禁止・停止条件

次に該当する場合、修正・検証または明示的な判断が成立するまで、対象差分を「改善完了」としない。

1. 既存の確定契約に反することが判明した。
2. 性能・資源などの重要な品質が、定めた許容範囲を超えて悪化した。
3. 作業によって安全性・権限境界・データ整合性を侵害する疑いがあり、検証できない。
4. 機能・仕様の意味変更が必要なのに、対象の変更契約が未確定である。
5. 効果の主張に必要な測定・比較がなく、実証済みであるかのように報告しようとしている。

測定できない事情そのものは、調査・低リスクの構造改善を全面禁止する理由ではない。ただし、**未測定の数値的改善効果を実証済みとみなしてはならない**。

### 2.4 不変条件が未確定の場合

仕様・既存実装・テストが食い違う場合は、(a)確定仕様、(b)利用者に観測される現行挙動、(c)既知不具合、(d)未定義の挙動を分離する。意味変更を伴わずに修正できる部分と、仕様の確定を待つ部分を切り分ける。仕様の未確定を理由に無関係な改善まで停止する必要はないが、未確定部分へ依存する変更は「契約未確定」と明記する。

### 2.5 仕様と実装が衝突するときの処理境界

確定仕様に反する現行挙動を記録するcharacterization testは、**退行検知用の観測記録**として扱う。正しい期待仕様への昇格や、テスト結果への都合の良い追従を禁止する。改善に意味変更が不可避なら、契約変更・不具合修正の独立条件へ分離する。

曖昧な仕様をAIが推測で確定してはならない。複数解釈があり実装を左右する場合は、仕様のownerに判断を求めるか、影響しない変更だけ進める。仕様根拠がない箇所について「安全な同等性を完全に保証した」と主張しない。

### 2.6 変更に伴う新規リスク

改善目的に直接関係しない限り、秘密情報・権限・認証・監査ログ・供給元・ライセンス・データ保持期間を変更しない。新依存の導入や既存依存の除去では、動作保証だけでなく保守・更新経路も比較する。重大な不可逆変更は上位の承認・安全規則に従う。

# 第 II 部　診断と対象選定

## 第3章　現行実装の分析・問題検出

### 3.1 現状調査の基本単位

現行リビジョン、関連仕様・Issue、実利用の処理経路、関連テスト、依存グラフ、性能基準値を確認する。解析対象は、利用者要求や観測問題と関係する実際の経路を優先する。表示上の呼び出し先と、実行時に使用される実装が異なる可能性にも注意する。

調査経路は「利用者・他モジュールの入口 → 実際の呼び出し先 → データ・状態の所有先 → 外部依存 → 出力・副作用」を基本とする。静的な参照探索だけで経路が確定しない場合は、実行時トレース・ログ・テスト等で補う。既存の共通機構を再利用する候補については、宣言上のAPIだけでなく実際の利用実績と互換性を調べる。

### 3.2 診断内容

| 領域 | 問題の兆候 | 確認手段の例 |
|---|---|---|
| L | 大量割当、メモリ増加、重複データ、過大バンドル | ヒープ追跡、資源計測、依存・成果物解析 |
| E | 不要ループ、重複計算、N+1 I/O、無駄な変換・転送 | トレース、クエリ計画、計算量分析、呼び出し回数 |
| P | 遅い起動、遅延の偏り、長いブロッキング、処理落ち | プロファイラ、負荷試験、フレーム追跡、p50/p95/p99 |
| S | 変更箇所の広域化、循環依存、責務混在、知識重複 | 依存グラフ、変更履歴、仕様追跡、変更シナリオ試験 |

### 3.3 証拠区分

問題候補には少なくとも次を区別して記録する。

- **観測事実:** 対象リビジョンと条件付きで実際に取得した数値・ログ・挙動。
- **解析による所見:** 静的解析、計算量・依存分析などから導いた構造的判断。
- **仮説:** 原因や改善可能性が未検証の説明候補。
- **未確認:** 必要な環境・データ・権限がなく、判定不能な項目。

警告数や「コードの臭い」の検出数を、実害や改善優先度へ直接変換しない。実害・変更頻度・仕様上の重要性へ対応付ける。

### 3.4 基準値の取得

改善前の計測値は、対象コミット、OS・ランタイム・ビルドモード・端末、入力データ、負荷・同時実行数、ウォームアップ、キャッシュ状態、試行回数、指標と単位を記録する。比較可能な測定を組めない場合は「基準値未取得」と明記し、先に計測環境の整備を検討する。

### 3.5 比較可能性と測定誤差

CPU/GPUの省電力制御、他プロセスの負荷、温度・スロットリング、I/Oキャッシュ、JITコンパイル、ネットワーク遅延、仮想化環境等が結果へ及ぼす影響を確認する。必要なら測定順序を交互にし、反復試行の中央値・分布・変動幅を残す。測定値の有効桁や比較方法は実際の測定精度に合わせる。極端に短い処理は計測オーバーヘッドを含むため、繰り返し実行や集約した測定を使う。

### 3.6 局所測定と実利用経路の対応

プロファイラのホットスポット、微小ベンチ、静的解析、変更履歴は異なる証拠である。局所指標を全体性能へ直結させない。計測値を外部の利用者価値へ接続する際は、`利用者操作または定期処理 → 実経路 → 対象箇所 → 最終的な時間・品質・資源`の対応を確認する。最終結果の測定が困難な場合は「局所改善のみ実証」と明記する。

再現性の乏しい問題では、観測条件と暫定的な再現手段を先に記録し、測定に必要なログ・プロファイルの取得自体が問題を変える可能性を検討する。センシティブなデータが必要な場合は匿名化・模擬入力を優先し、実データや認証情報を外部へコピーしない。

### 3.7 診断対象と非対象の明示

D0では詳細な全域監査をしないことを明記し、D1/D2では「調べた領域」「調べなかった領域」「基準値不足」「具体的な拡張理由」を区別する。候補の存在は不具合の確定や変更の許可を意味しない。

## 第4章　改善候補の評価・優先順位

### 4.1 候補ごとの判定項目

候補は「原因 → 変更手段 → 期待される効果 → 影響範囲 → 検証方法」の対応で記述する。少なくとも次を比較する。

- 利用者・運用・開発上の損失の大きさと発生頻度。
- 直接の改善効果（測定可能な場合は推定幅と根拠）。
- 契約・互換性・安全性・品質予算へのリスク。
- 実装、計測、レビュー、移行、保守の総コスト。
- 独立して変更・検証・復旧できる範囲。
- 放置した場合の損失と、他作業の前提になる度合い。

### 4.2 優先判断

セキュリティ・データ破損等の既存の高優先度問題は、単なる見通しの悪さより優先され得る。ただし本書は新たな一律優先度表を作らず、案件の目標・リスク・既存の開発運用上の優先順位に従う。

改善候補は、**実行 / 先に計測 / 先に仕様確定 / 別Issueへ分離 / 保留 / 不採用**のいずれかへ分類する。低価値な項目を発見しただけで実装タスクへ自動昇格させない。

### 4.3 停止を含む最適化

明確な価値がない改変、測定誤差以下の便益、検証費用に見合わない候補、ほかの品質へ過大な副作用をもたらす候補は実行しない。改善候補の数・修正ファイル数・行数削減量を成果指標としない。

### 4.4 改善仮説の採否と再評価

改善案ごとに「この変更が効く理由」「効果がないことを示す反証」「目的を満たすより小さな代替案」を記載する。優先順位付けで恣意的な点数・重みを必須化しない。効果予測が不確かな場合は、限定された試験や観測で不確実性を減らすことを候補とする。改善の実施後は、実測に基づき優先順位を更新し、初期計画を自己目的化しない。

# 第 III 部　改善手段と適用条件

## 第5章　軽量化（L）

### 5.1 目的と主要指標

同等の要求を満たすために消費する資源を減らす。代表指標は、常駐メモリ、ピークメモリ、アロケーション量、配布サイズ、ディスク使用量、データ転送量、CPU 稼働量、電力消費等である。測るべき指標は対象システムの制約から選定する。

### 5.2 改善候補

- **所有・寿命の整理:** 不要に保持するデータ、リーク、解放遅延、複数層での同一情報保持を減らす。
- **割当とコピー:** 高頻度の短命オブジェクト、不要な中間配列、直列化・複製を減らす。
- **読み込み範囲:** 不要なアセット・モジュール、未使用コード、不要な機能同梱を削減する。
- **データ構造:** サイズ・アクセス特性・更新頻度に応じた表現へ切り替える。
- **キャッシュとバッファ:** 過大保持・多重キャッシュを抑え、必要な寿命と容量を設定する。
- **依存整理:** 重複・未使用依存を確認し、代替実装の保守コストを含めて廃止可否を判断する。

### 5.3 除外と副作用

データ圧縮は展開時間・CPU負荷を増やし、遅延読み込みは初回待機を増やし得る。メモリ節約のための再計算は高速化に反する場合がある。依存削除に伴いセキュリティ更新・互換処理を独自実装するなら、逆に総保守負担が増える可能性がある。

**採用条件:** 選んだ資源指標が比較可能な条件で改善し、規定された応答・安定性・互換性を損なわない。

### 5.4 「削減」か「負担の移転」かを判定する

起動時読込を遅延化した場合、総データ量が減ったのか、単に別のタイミングへ移ったのかを区別する。ローカルメモリからディスク・通信・GPUへ負担を移した場合も同様に、**対象資源の削減**と**資源負担の移転**を区別して報告する。容量・電力・CPU使用率は条件によって相互変換できないため、測定指標を固定する。

### 5.5 軽量化固有の検証範囲

メモリでは、平均・常駐・ピーク・割当頻度・長時間稼働後の増加を必要に応じて区別する。ファイル・通信では圧縮前後のサイズだけでなく読込・展開・CPU・ピークメモリを評価する。依存整理では、サイズの減少と別に、互換性・ライセンス・供給元・セキュリティ更新・再現ビルドの可否を確認する。構造的な削除が実測資源の削減を伴わない場合は、その目的をSとして評価する。

## 第6章　効率化（E）

### 6.1 目的

必要な結果へ到達するまでの**仕事量そのもの**を減らす。実行時間だけではなく、計算回数、走査量、I/O回数、転送量、再描画回数、ビルド・テスト等の作業量も対象とする。ただし開発工数の削減は実行効率と分けて記録する。

### 6.2 優先する診断順

1. 不要な処理がそもそも発生していないか。
2. 同じ結果を複数箇所・複数回生成していないか。
3. 対象データを必要以上に走査・転送・コピーしていないか。
4. アルゴリズムとデータ構造が実際の入力規模に適しているか。
5. 必要な処理を、適切なバッチ化・遅延処理・差分更新にできるか。

### 6.3 代表手段と適用境界

検索索引、適切なキャッシュ、バッチ I/O、差分更新、クエリ最適化、計算結果の再利用、ベクトル化、処理順序の変更、データ局所性の改善などを候補とする。採用に際しては、最新性、処理順序、並行性、例外、無効化条件、メモリ・同期コストを確認する。

**禁止される短絡:** 「ループを減らしたから効率的」「非同期・並列にしたから効率的」「キャッシュを増やしたから速い」と、実行経路や仕事量を確認せず断定しない。

### 6.4 実行効率と開発効率を混同しない

実行時の計算量削減と、ビルド・テスト・レビュー・修正などの開発工数削減は別の改善目的として記録する。共通化は変更工数を減らしても、実行時の間接呼び出しやデータ変換を増やす場合がある。開発効率の評価には、実際の変更シナリオ・テスト時間・手戻り・変更波及範囲などを使い、推測の「工数削減率」を断定しない。

### 6.5 並列・非同期・キャッシュの採否

並列化や非同期化は、総CPU時間を減らさず待機を隠すだけの場合がある。同期・競合・失敗時の再試行・順序保証の追加費用まで含めてEを評価する。キャッシュは有効期限・失効条件・二重更新・メモリ負担を明記し、古い結果を返す可能性が仕様に反しないか確認する。性能や効率が増しても冪等性・データ整合性・精度を侵害する方式は採用しない。

## 第7章　高速化（P）

### 7.1 計測を先行する

高速化は、利用者または処理要件に対応する指標を定義した後に実行する。平均だけでなく、対象に応じて中央値、p95、p99、最大値、フレーム期限超過率、スループット、起動時間等を用いる。入力規模や混雑条件が異なる結果をそのまま比較しない。

### 7.2 ボトルネックの選定

CPU・メモリ・GPU・I/O・待機・ロック競合・ネットワーク・DB・UI描画など、遅延の原因を区別する。全処理の小部分にしか寄与しない箇所の最適化は、全体への改善上限を見積もってから着手する（Amdahl の法則）。

プロファイラで得た呼び出し数や累積時間と、独立したベンチマークで得た全体実行時間は用途が違う。計測器のオーバーヘッドを考慮し、比較には適したベンチマークを用いる。

### 7.3 手法の選択

アルゴリズム・処理回数・データ移動の改善を先に検討し、その後に対象経路の演算最適化、バッファリング、並列化、SIMD、キャッシュ局所性、レンダリング最適化等を選ぶ。ただしハードリアルタイム等では局所最適化が必須となることもある。

### 7.4 比較・判定

Before / After を同じ環境・入力・測定条件で繰り返し測定する。必要に応じて測定順序を交互にし、ノイズやウォームアップの影響を調べる。観測差がばらつきに埋もれる場合は「改善未立証」とし、明確な効果を示すまでは数値の誇張をしない。

数値精度・消費メモリ・電力・フリーズ頻度が速度とトレードオフになる場合は、当該予算との整合を別に検証する。

### 7.5 ベンチマークの結果と再現性

比較では原則として同一の成果物形態・ビルド設定・入力・負荷・測定器を使用し、差分の説明に必要な試行回数とばらつきを示す。Release/Debugやコールド/ウォームの混同、別端末の単純比較、非代表的な微小ベンチだけによる全体高速化の主張を避ける。対象の実利用経路におけるエンドツーエンドの結果を、局所ベンチマークと区別して確認する。

統計上の有意性、効果量、再現性は別の概念である。厳密な統計検定を全変更へ強制せず、実際のばらつきに対して改善が十分大きいかを判定する。時間が厳密な処理では「平均は改善、期限超過率は悪化」のような結果を見落とさない。

### 7.6 速度の意味を利用者経路で固定する

処理単体の高速化、UI操作への応答、スループット、リアルタイム期限、起動完了時間は異なる指標である。利用者に影響する指標が未定義のまま「高速化」を完了としない。必要に応じて、待機時間やバックグラウンド処理の増加など、遅延の単なる移転を区別する。

### 7.7 計測結果の比較方法を先に固定する

Before/Afterで同一負荷を複数回実行し、同条件で比較する。中央値・分位点・分布・試行回数・測定ノイズのうち、対象の判断に必要なものを事前に定める。可能なら実行順序を交互にする等、環境ドリフトを抑える。原因が判明した不正な測定は根拠を残して再測定するが、望ましくない測定値だけを恣意的に除外しない。

**有意差と実用価値を混同しない。** 改善量が測定ノイズより十分大きいこと、かつユーザー要求に対して意味のある差であることをそれぞれ検討する。試験回数・統計検定手法・閾値を全案件に一律固定しない。数値改善が確認されなくてもSの目的で別途採用することはあるが、Pの成功と記載しない。

### 7.8 リアルタイム・高負荷・低頻度処理

ハード／準リアルタイム処理では、平均処理時間だけでなく期限超過・ジッタ・バッファアンダーラン・割当・停止要因などを優先する。Web/UIでは実操作経路の応答と高分位遅延、APIでは同時実行数・失敗率・後端依存、起動処理ではコールドとウォームを分ける。非代表的なテスト条件から全利用環境の性能を保証しない。

## 第8章　構造改善・責務分離・平易明瞭化（S）

### 8.1 目的

理解・修正・拡張・検証に必要な作業を減らし、変更理由が無関係な箇所へ波及しない構造へ近づける。既存 Core Source にある「変更理由による分離」「同一知識の一元化」「情報隠蔽」を具体的な診断と移行へ変換する。

### 8.2 診断単位

- **変更理由:** 何が変わるとその要素を修正するか。異なる変更理由が同一モジュールへ混入していないか。
- **情報の所有:** 同じルール・定数・変換規則が複数箇所で独立管理されていないか。
- **依存の方向:** 変更頻度の高い詳細へ上位機能が過度に依存していないか。循環依存が生じていないか。
- **状態の境界:** 誰が生成・更新・破棄するかが明確か。同期・不変条件が隠れていないか。
- **公開契約:** 実装都合を過剰に公開していないか。インターフェースの利用者を特定できるか。
- **可読・変更コスト:** 実際の変更シナリオで修正箇所・必要知識・テスト範囲が減るか。

### 8.3 共通化・再利用

類似コードを機械的に一つにしない。**同一の知識・仕様・変更理由を共有する**場合に共通化候補とする。似ていても異なる仕様・独立した変更理由を持つ場合は、共通化による条件分岐・結合の増大を比較する。

同等機能が既に提供されている場合は、現行正本・公開 API・バージョン・依存関係・互換性を確認してから再利用を優先する。特に repository を跨ぐ共通モジュールは、所有者、変更手続、互換方針、利用側の検証経路を定義する。単に「共通 API がある」という理由だけで移行を完了したとみなさない。

### 8.4 過剰分割・過剰抽象化の抑制

モジュール数・層数を増やせば責務分離したことになるわけではない。細分化によって依存を追う回数、インターフェースの数、実装を理解するための移動量が増える場合、統合した方が平易になる可能性がある。変化が確認されていない将来想定のために汎用フレームワークを導入しない。

### 8.5 削除と廃止

不要に見えるコードでも、旧データ互換、外部呼び出し、ビルド・運用経路、フォールバック、テスト専用機能として使用される可能性がある。参照探索・実行経路確認・互換確認を経て削除する。移行途中の旧実装・フラグ・アダプタは期限または撤去条件を明示し、永久的な二重管理へしない。

### 8.6 構造改善の実証

静的指標（循環依存、モジュール間の接続、重複知識の減少等）は補助証拠とする。可能なら「同種の機能変更なら何箇所を触るか」「一つの規則変更をどこだけで完結できるか」等の具体的な変更シナリオで、理解・変更・テストの負担を比較する。

### 8.7 技法の選択と適用除外

| 観測問題 | 検討できる手段 | 適用を避ける・再評価する条件 |
|---|---|---|
| 一つの処理へ異なる変更理由が集中 | 関数・モジュール抽出、境界の再配置 | 分割によって状態共有と相互依存が増える |
| 同一規則を複数箇所で保持 | 正本の一元化、共有機構の利用 | 仕様・変更理由が異なり、統合が分岐を増やす |
| 内部表現が外部へ露出 | 情報隠蔽、限定したAPI | 隠蔽層がほぼ転送のみで価値を持たない |
| グローバル状態や更新経路が不明 | 状態所有者の明確化、依存注入 | 所有関係がむしろ複雑化し、寿命管理が破綻する |
| 条件分岐が複雑 | 意味ごとの抽出、状態遷移・データ駆動化 | 小規模・安定した条件へ過剰な抽象化を導入する |
| 旧実装が永久に残る | 利用先の移行、互換層の撤去 | 外部利用先・旧データ互換を確認できていない |

これらは技法の強制順位ではない。問題と適用条件を確認した後で選ぶ。設計パターン名・メトリクスの良化・ファイル分割数を改善理由の代替としない。

### 8.8 構造改善の証拠の強弱

構造改善の根拠は、少なくとも「具体的な変更困難があった箇所」「何を変更したか」「変更後に何が局所化・明確化されたか」を結び付ける。実際の変更シナリオによる比較、依存グラフと変更履歴の照合、公開契約とテスト境界の縮小等を優先し、単なる主観的な読みやすさや静的スコアだけには依存しない。計測できない項目は定性的根拠として、未測定を明示する。

### 8.9 既存機能・共通APIの再利用判定

managed repositoryで同等のロジック・数値操作・入力UI・共通部品を新規作成・変更・統合する場合は、devflowの再利用優先契約を適用する。改善作業では以下を確認する。

1. **名前ではなく意味を比較する。** 入出力、単位、許容域、状態所有、例外・リセット、UI操作・アクセシビリティ、同期・非同期などを具体化する。
2. **現行の所有元と実装を探索する。** capability catalog、実際の公開entrypoint、code、tests、関連Issueを照合し、ファイル名・シンボル・古い記録だけで判断しない。
3. **三類型へ分類する。** A: 意味同一なら既存機構を利用。B: 同じ責務で差分があるなら所有元の拡張、設定化、薄いadapterを検討。C: 意味・変更理由が独立するなら別実装を容認し、その区別を記録する。
4. **利用元まで検証する。** 単体の戻り値だけでなく、UI表示・操作・誤入力・保存互換・性能・消費側の実行経路を確認する。
5. **重複解消の出口を決める。** 旧実装の利用者、互換レイヤー、撤去条件、未移行箇所、例外のowner・再評価契機を記録する。

同一知識が複数Repositoryへ存在していても、単に中央へ移すことを目的としない。共通APIの変更権限・バージョン・所有責務・消費側の依存コストが不利なら、同一化のための新たな結合を増やさない。既存contractが互換で再利用可能であるかは、現在の実装と実際の利用で確認する。

### 8.10 構造的な改善の反証シナリオ

構造改善の採用前に、代表的な将来変更を一つ以上想定し、関連する仕様変更が必要になった場合の編集箇所・依存・テスト範囲・理解負担を比較する。変更シナリオは仮想ケースであることを明示し、実装工数の削減が実測されたかのように記載しない。導入した抽象層で利用者が一箇所修正する代わりに多数のadapterを更新する必要があるなら、改善仮説を再検討する。

## 第9章　複数領域の相互作用・全体判断

### 9.1 独立指標と制約指標

対象の改善指標と、悪化を抑制する制約指標を分離する。たとえばキャッシュは P を改善しても L や S を悪化させる場合がある。抽象層の追加は S を改善しても P を損なう場合がある。縮小した配布物が初回起動を遅くする場合もある。

### 9.2 判断手順

まず契約・安全条件を守る。次に、対象目的に対する実測・実証の便益を比較する。複数候補間で優劣が一意に決まらない場合は、利用条件・運用コスト・変更頻度・後戻りの容易さを比較し、採否理由を記録する。

4領域を単純に足し合わせた「総合点」や、共通根拠のない固定重みは使用しない。**1領域の改善を他領域の重大な悪化で相殺して承認しない**。案件の目的が許容するトレードオフのみ採用する。

### 9.3 制約と目的の分離

改善目標に対して、(a)絶対に守る契約、(b)許容値を持つ品質制約、(c)最大化・最小化する目的指標、(d)未評価の影響を分類する。制約違反を重み付き総合点で打ち消さない。目的間に優劣が付かないときは、案件の利用者・変更頻度・運用条件へ戻って採否を判断する。

### 9.4 初期目的の事後変更

改善結果が期待を下回ったからといって、事後的に指標・許容差・受入条件を緩めてG3合格にしない。新しい知見で目的を変える必要がある場合は、元の判定と変更理由を保存し、仕様・受入条件の更新を別の意思決定として扱う。

### 9.5 トレードオフ判定の境界

目的指標を改善していても、定めた不可侵契約または品質上限を破るなら、変更案の別モードへの隔離・仕様変更としての再審議・撤回を検討する。既存の正本で許容可能な選択肢が複数ある場合は、利用形態ごとの便益・追加保守コスト・復旧可能性を比較する。評価不能な項目は「品質を保持」と記さず未検証として扱う。

**例（概念例・固定要求ではない）:** キャッシュ追加でp95が改善しメモリ使用量も増加した場合、メモリが許容範囲内で、失効・整合条件も満たすなら採用可能である。一方メモリ上限を破る場合、速度の改善だけで採用してはならない。

# 第 IV 部　変更実行・検証

## 第10章　実行単位・段階的移行・統合

### 10.1 作業単位

可能な限り、一つの差分で一つの改善仮説と検証条件を明確にする。無関係な修正を同時に含めない。変更を小分けにすること自体が目的ではなく、**独立して理解・検証・統合・復旧できる単位**を選ぶ。小さく分けすぎて中間状態が壊れたり意味が読めなくなったりする場合は、機能的に完結した単位へまとめる。

### 10.2 大規模な置換

影響範囲が広く、一度に置換すると比較・復旧が困難な場合は、抽象層や切替機構を用いた段階移行を検討する。旧・新実装の同時動作、差分比較、利用先の順次移行、旧機構の撤去条件を設計する。ただし、これらの移行機構の導入・保持コストを上回る効果が必要であり、小規模修正へ一律導入しない。

### 10.3 実装の進め方

1. 変更前契約・影響・基準値・受入条件を確定する。
2. 必要なら回帰テスト・基準測定を追加して既存挙動を保護する。
3. 変更単位ごとに実装し、その単位で成立する検証を実施する。
4. 対象経路の実稼働確認と必要な広域回帰を実施する。
5. 受入条件を満たした変更のみ、既存の権限・レビュー・CI規則に従って統合する。
6. 自らの変更で生じた参照・仕様・テスト・進捗記録の不整合を修正する。

### 10.4 巻き戻しと変更競合

大規模・互換リスクのある変更では、復旧手段と旧データ・旧設定の可逆性を先に確認する。共有ブランチの強制変更、破壊的マイグレーション、公開・デプロイ等は既存の Human gate を適用する。並行作業中の他者所有範囲へ無断で衝突する変更を行わない。

### 10.5 変更の切り分けとレビュー

原則として意味変更・不具合修正・構造改善を独立してレビューできる単位へ分ける。ただし名称の局所修正など、切り分けることで逆に理解・検証が難しくなる軽微変更は同一単位に含められる。テスト追加・計測基盤の整備が安全性の前提となる場合は、実装変更より先行させる。変更量の行数・PR数を最適化目標にしない。

### 10.6 段階移行の退出条件

一時的なFeature flag・アダプタ・二重実装には、所有者、対象利用先、移行完了条件、旧側を撤去できない理由、撤去後の回帰確認を設定する。二重書き込み・互換変換はデータ不整合を生み得るため、読み書きの正本と切替手順を明示する。

### 10.7 repositoryを跨ぐ変更

複数repoのownerが存在する場合、共通機構側・利用側の契約改訂を分離し、互換性維持期間・利用先切替・旧APIの撤去条件を定める。横断の調整情報と各repo固有の技術仕様を別々の正本に保存し、一つのrepoのPR成功を他repoの受入成功に読み替えない。機能が実際に使われるconsumer経路での確認を伴う。

### 10.8 変更・レビュー・CI・統合・公開を区別する

コード差分が完成したこと、ローカルテストが成功したこと、正式Reviewが成立したこと、CIが通ったこと、mainへmergeされたこと、配布・公開環境で機能したことは、それぞれ別の状態である。既存のdevflowと対象repoの受入条件に従い、必要なステップだけ実施する。独立Reviewが必要かは変更の安全影響と既存のreview policyに従い、本書だけで一律の独立Reviewer・追加PRを義務付けない。

## 第11章　検証・評価・受入ゲート

### 11.1 3ゲート

| ゲート | 問い | 判定証拠 | 不合格時 |
|---|---|---|---|
| G1 契約保持 | 守るべき外部挙動・データ・互換条件を保ったか | 仕様対応テスト、境界・統合・実稼働経路での検証 | 修正または意味変更として分離 |
| G2 品質非退行 | 対象外の品質が許容値を超えて悪化していないか | 性能・資源・安定性・安全性・運用の回帰 | 修正・撤回・許容差再検討（勝手に緩和しない） |
| G3 目的達成 | 狙った改善が観測・実証されたか | 同条件 Before/After、構造変更シナリオ、依存差分 | 効果未立証・保留・撤回・別候補の検討 |

G1/G2 は対象に応じて適切な範囲を定義する。G3 は目的に対応する指標ごとに判定する。数値で直接測れない構造改善も、具体的な変更波及・責務・依存・保守シナリオを根拠として明示する。

### 11.2 テストが存在しない場合

テスト不足を理由に無制限な書き換えへ進まない。必要なら既存動作を記録する characterization test、仕様から導く境界テスト、差分実行・比較試験を準備する。**観測した既存の不具合を、正しい契約として恒久化しない。**

### 11.3 計測の一貫性

比較時は測定対象・単位・環境・サンプル・負荷・計測モード・キャッシュ・ウォームアップを揃え、変更前後の結果、測定ばらつき、未評価の条件を残す。実環境に依存する性能を、コード読解やスクリーンショットだけで実証したとみなさない。

**時間短縮率の例:** `(T_before - T_after) / T_before × 100%`。これは測定条件が等しく、時間が短いほどよい対象へ適用する。メモリ、スループット、品質指標等を同式で一律に評価しない。

### 11.4 テスト品質

既存テストが通過しても、重要な不変条件が未検証なら G1 の完全な根拠にならない。必要に応じてテストデータの代表性、境界、異常系、実利用経路、変異テスト等を確認する。網羅率だけで欠陥検出能力を保証済みとみなさない。

### 11.5 判定状態・限定受入・例外境界

各ゲートは、`not_evaluated`（未実施）、`pass`（合格）、`fail`（不合格）、`inconclusive`（検証済だが判定不能）、`not_applicable`（事前に非適用と確定）の5状態で記録する。`not_applicable` は、当該目的・影響範囲に当てはまらない明示的な理由が必要であり、測定不能の言い換えには使わない。

通常の変更承認の根拠は、必要範囲での G1 `pass`、G2 `pass`、改善目的に対応するG3 `pass` とする。G1/G2 の重要項目が `fail` または `inconclusive` のときは「安全に改善済み」とせず、追加検証・修正・撤回・適切なowner判断へ切り分ける。目的が単なる調査や測定基盤整備である工程は、その工程自体の受入条件と、後段の改善成果（G3）を混同しない。

**限定受入:** 一部の非必須項目が未検証でも、その項目が変更の実際の影響範囲と受入目的に関係しないことを説明でき、重要な契約・安全・品質条件は必要範囲で検証され、既存の許可・review・CI規則で統合可能な場合に限り、限定された変更単位の受入を検討できる。**重要なG1/G2項目が未検証・不合格のまま、限定受入で通過させない。** これをG1/G2/G3全域 `pass` と表記しない。統合可否と「改善効果を実証済み」の判定も分離する。

結果の総合状態は `not_evaluated / adoptable / conditional / benefit_unproven / contract_or_quality_failure / verification_blocked / rejected` のいずれかで記録する。各ゲート結果を隠して集計名だけ残さない。

### 11.6 受入証拠の妥当性

| 改善目的 | 受入の中心証拠 | 単独では不十分な証拠 |
|---|---|---|
| L | 資源使用量の同条件比較、上限制約の確認 | ソース行数、削除ファイル数 |
| E | 処理量・データ移動・I/O回数や開発変更工数の比較 | ループや関数の数だけの比較 |
| P | 代表的な実行経路での時間・遅延・スループット分布 | 静的コード読解、微小ベンチだけ |
| S | 変更理由・責務境界・依存・変更シナリオに基づく具体的な比較 | 読みやすさの自己評価、静的スコアのみ |

単独の証拠が不十分でも、対象の性質・リスクに応じて複数の補助証拠を組み合わせて判断する。機械的に観測可能な項目を、人間による確認だけへ安易に委ねない。計測困難な構造改善について、根拠のある質的評価を数値的に実証済みと表記しない。

### 11.7 再計測・長期的な退行管理

実行環境・コンパイラ・ライブラリ・負荷条件の変化で最適化効果が失われ得る場合は、再評価の契機を定める。再測定はその条件が成立したときに限り、恒久的に全ベンチマークを全PRで動かすことを義務付けない。重要経路では、適切な頻度での性能回帰検知を検討する。

### 11.8 指標と閾値を後から選ばない

評価対象、入力分布、比較する指標、許容値、主要な制約は原則として変更前に決める。改善後に都合の良い指標だけ選ぶことを避け、明らかな測定上の欠陥が発見された場合は欠陥・変更理由・再試験結果を追跡可能にする。事後的な仕様変更が必要なら、旧条件に対する判定を保持した上で、新条件で新たに評価する。

### 11.9 対象別の検証例と適用除外

以下は方法を例示するものであり、技術別の固定閾値を定めない。

| 対象 | 重点的に確認する契約・退行 | 改善効果の代表証拠 |
|---|---|---|
| DSP/音声処理 | サンプル精度・位相・遅延・アーティファクト・実時間期限・エラー時の継続性 | 数値差・スペクトル指標・期限超過・CPU/割当の再現可能な比較。単一の数値だけで聴感品質を完全に証明しない |
| Web/UI | 操作手順・選択状態・Undo/Redo・アクセシビリティ・表示内容 | 実操作E2E、描画・入力遅延・メモリ・バンドルの比較 |
| API/DB | データ整合・トランザクション・権限・エラー・並行性 | 実クエリ計画・処理量・負荷別遅延分布・失敗率 |
| CLI/バッチ | exit code・標準入出力・保存互換・再実行条件 | 代表入力群での処理時間・資源量・正答率 |
| ライブラリ/共通部品 | API互換・所有元・consumerの利用経路 | 依存グラフ・移行率・統合テスト・代表的な変更シナリオ |

機械的に評価できない知覚・品質要求が残る場合は、その範囲・利用可能な代理指標・人間判定の必要性を区別する。代理指標を完全な品質保証とみなさない。

# 第 V 部　AIによる実行・運用

## 第12章　AIエージェントの実行規則・大局判断

### 12.1 依頼の解釈

「軽量化・効率化・高速化・責務分離を進める」という依頼は、依頼範囲に応じた**D1またはD2の診断を通じて4領域の問題候補を見つけ、根拠がある変更を選んで実施する**ことを意味し、必ず各領域にコード差分を作ることではない。通常の局所的な機能修正・バグ修正ではD0を基本とし、根拠なく全領域へ作業を拡大しない。指定されていない機能を追加したり、従前仕様を一般的ベストプラクティスで置換したりしない。

### 12.2 AIが記録する最低情報

- 対象案件・リビジョン、上位目標、適用する仕様と権限境界。
- L/E/P/S の各領域で発見した候補または「未検出／未確認」の理由。
- 取り組む候補、問題と原因の証拠、期待効果、別案、変更影響。
- 改善前基準値、G1/G2/G3 の受入条件、実測結果と証拠の所在。
- 作業状態、次の実行単位、blocker、戻し方、未完了条件。

既存の devflow / Repository Control / Issue / PR 等の正式な記録面を使用し、本資料のためだけに競合する新たな進捗台帳を増設しない。現在のリポジトリ状態は live で確認する。

### 12.3 実行ループ

`上位目的確認 → 現状・契約確認 → 4領域の範囲付き診断 → 候補評価 → 変更単位決定 → 改修 → G1/G2/G3検証 → 記録面整合 → 大局判断`

大局判断の結果には `続行`、`経路変更`、`別Issueへ分離`、`保留`、`終了` を含める。目的と受入条件が満たされた場合、関連性だけを理由とする追加修正を開始しない。未達条件が存在する場合も、毎回同じ診断を最初からやり直さず、状態変化と未完了部分を重点確認する。

### 12.4 エージェントの自律範囲

既存の開発原則・権限・レビュー・CI・安全ゲートに従い、承認済み範囲での調査、テスト追加、低リスク変更、PR作成、条件を満たす安全な統合を遂行できる。本書単独で新たな release/deploy、権限変更、credential 操作、破壊操作、公開を許可しない。

### 12.5 終了判定

案件の完了には、(a) 対象範囲と改善目的が明示されている、(b) 受入ゲートの判定と証拠が記録されている、(c) 未完了・保留・非対象が区別されている、(d) 必要な統合・復旧・記録面整合が完了していることを要する。4領域に変更差分が均等に存在する必要はない。

### 12.6 AIの証拠・判断の独立性

AI自身の説明、「修正済み」「高品質になった」などの宣言、テストを緩めた結果だけを受入根拠にしない。失敗したテストの削除、測定条件の有利な変更、事後的な許容差緩和、実行しなかったテストを実行済みとする記録を禁止する。検証器自体を変更した場合は変更理由・テスト妥当性を別に確認する。独立レビューが求められる条件は既存の運用正本に従う。

### 12.7 運用負担の上限制御

D0の局所作業へ一律の診断票・広域依存グラフ・性能ベンチを強制しない。D1/D2でも既存のIssue/PR/計測記録を再利用し、同じ情報を複数台帳へ複製しない。停止条件に該当した場合は原因・必要操作・検証状況を記録して適切に保留する。安全性と改善効果を確認済みの作業を、形式的な追加分析だけのために延期しない。

### 12.8 live devflowとの責務境界

本書のD0/D1/D2は診断深度、G1/G2/G3は改善品質の判断補助であり、devflow側のPriority/Tier・監査状態・Formal Review・CI・Human gate・Claim/Issue/PR状態・release承認を代替・変更しない。具体的なissue作成、checkpoint、Session、review、merge、公開の要否は、実行時点のdevflowと対象repoの規則に従う。

本書により自動的に新Issueを生成するものではない。既存のowner Issueがあり、当該改修がその受入条件の一部なら再利用する。影響が独立する別問題で、作業の分離が実際の実行・検証・復旧に有効な場合のみ別Issueとする。

### 12.9 報告と本書の適用確認

開発チャットでは、詳細な証拠・経過はIssue/PR/CI等の既存面へ残し、ユーザーへは対象・実際に改善した点・計測/検証結果・残余リスク・次に必要な行動を簡潔に伝える。D0/D1/D2やG1/G2/G3を説明するだけで、コード変更・改善の受入が成立したとみなさない。既存正本を確認できない場合はアクセス状況を明記し、確認済みと偽らない。

**開始前:** 対象仕様・リビジョン・変更範囲・利用経路・既存テスト・安全境界を確認したか。診断深度D0/D1/D2を選び、その深度で必要な領域を確認したか。何で合格とするかを事前に決めたか。

**統合前:** G1/G2/G3 は対応する証拠を持つか。意図せぬ仕様変更・新たな負債・旧実装との二重管理がないか。記録と現行実装は整合するか。

**終了時:** 目的未達の具体的条件があるか。なければ止める。残る改善候補は必要性を判定して別Issue・保留・不採用とし、自動的に作業拡大しない。

**判定書式（最小）:** 対象リビジョン / 改善目的 / 事前受入条件 / 実証した領域 / G1・G2・G3の状態 / 変更後の観測 / 未確認 / 採否・戻し方 / owning Issue・PR・CI参照。関連する情報が既存のIssue/PRにある場合、同内容の新資料を作らず参照を残す。

# 付録 F　技法の選択例（非規範）

| 問題 | 仮説 | 検証すべき指標/条件 | 候補技法 | 撤回・再検討の条件 |
|---|---|---|---|---|
| UI操作ごとの全件再計算 | 無関係な更新で同じ処理が走る | 実呼出回数、入力応答、キャッシュ一貫性 | 差分計算・依存の局所化 | 変更後に古い状態を表示 |
| 大量データの起動時一括読込 | 必要になる前のデータ取得が多い | 初回表示・総待ち時間・転送・メモリ | 遅延読込・分割転送 | 遅延がユーザー操作へ移転し悪化 |
| 似た入力制御の独自実装が分散 | 同じ意味を異なる処理が担う | capability契約、実利用UI、入力境界・保存互換 | ownerの共通APIへ移行 | 差異が仕様上独立していた／所有元のAPIが不適合 |
| 高負荷の音声処理で期限超過 | 割当・同期・演算が実時間を圧迫 | 期限超過率、ジッタ、位相/精度・CPU | 割当排除、バッファ再利用、処理順序最適化 | 音質・精度・安全な復帰が悪化 |
| リポ横断で一つの仕様変更が広域へ波及 | public contractと実装詳細が混在 | API契約、consumer依存、変更シナリオ | 情報隠蔽・versioned adapter | 移行負担や結合が増え、変更箇所が減らない |

上表は技法を自動指定するものではない。実際の改善は、原因の確認・適用条件・契約・G1/G2/G3証拠に従って選択する。

# 付録 G　用語

- **リファクタリング:** 外部の契約上の振る舞いを維持しながら内部構造を改善すること。
- **最適化:** 特定の制約・評価指標に対して、性能や資源効率などを改善すること。
- **不変条件:** 作業の前後で保持することを要求された性質。
- **非退行:** 変更対象外の品質や既存機能が、許容条件を超えて悪化していないこと。
- **プロファイリング:** 処理負荷・時間・資源消費の分布を計測して分析すること。
- **Characterization test:** 既存実装の観測挙動を記録し、意図しない変更の検出に用いるテスト。
- **Mutation testing:** 人工的な欠陥に対するテストの検出能力を調べる手法。
- **p95 / p99:** 値の95% / 99%がその値以下になる分位点。
- **ADR:** 設計判断の理由・代替案・再検討条件等を記録する文書。
- **D0/D1/D2:** 本書独自の診断深度区分。軽微な影響確認、対象診断、広域診断を分ける。
- **G1/G2/G3:** 本書独自の受入ゲート区分。契約保持、品質非退行、改善実証を分ける。
- **エンドツーエンド:** 利用者や他システムの入口から結果が出るまでの実際の処理経路。
- **Feature flag:** 旧新機能や実装経路などを切り替えるための制御機構。
