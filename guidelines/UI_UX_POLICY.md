# UI / UX ポリシー

## 設計原則
- 操作効率、標準操作慣習、状態・文脈継承、回復可能性、暗黙の操作期待の正本は `USABILITY_POLICY.md` とする。UI/UX側では、それらを画面構造・視覚階層・状態表示へ反映する。
- データベースのテーブルや内部変数名など実装の複雑さをユーザーに見せず、UIはユーザーの意図やドメイン概念を反映する。
- 内容を減らすのではなく、ユーザーが覚えたり比較したり検索したり保持したりする負担を減らす。
- 関係や階層を構造で示す。比較、一覧、入力に適する場合はテーブルやフォームを使い、直接操作は対象・安全性・実装環境に適する場合に優先する。
- UIは情報閲覧だけでなく、対象ユーザーの仕事を進めるための道具として設計する。CRUD管理画面が目的に適する場合まで排除しない。
- 編集や操作時には即時の視覚フィードバックを行い、外部トリガーが必要な場合は明示的に配置する。
- 編集中の対象を明確にし、選択中の項目を強調し、操作部の位置を一貫させる。
- 編集頻度、破壊性、実装可能性に応じて、Undo/Redo、復元、確認、履歴のいずれかを用意し、回復手段を明確にする。
- 参照切れや無効状態のデータは自動削除せず、問題を視覚的に示し、修復手段を提供する。
- PC用とモバイル用のUIを別々に設計し、単純に縮小しない。
- レイアウトやタイポグラフィ、色についてデザイントークンを用い、一貫性を保つ。
- 状態変化や作用範囲、関係を説明文に頼らず、視覚的に把握できるようにする。
- 不要な多方向スクロール、ネストされたスクロール領域、隠れた状態を避ける。主作業が複数領域を必要とする場合は、各領域の役割と現在位置を明確にする。
- タグは分類用途にのみ用い、エンティティの属性そのものをタグへ押し込まない。
- 編集・閲覧・デフォルトなど複数の状態を簡単に切り替えられるようにし、別画面への遷移を必要最小限にする。

## 利用者起点の情報・操作設計

本ポリシーのUI表現は、`USABILITY_POLICY.md` の UX-01〜UX-16 を上位原則とする。画面は「指定されたUI部品を設置したか」ではなく、「利用者が何をしたくて何を当然期待するか」から構成する。共通の標準操作そのものは Usability Policy、具体的な部品実装は UI protocol pack の対応規約を正本とする。

- **操作と発見手段を分離しない**：利用者が対象から自然に操作を見つけられる位置、メニュー、ラベル、状態表現を優先する。不可視の長押し・ショートカットのみを唯一の経路にしない。
- **ショートカットは操作箇所で示す**：割当がある場合、該当するメニュー項目等で組合せを確認できるようにする。機能一覧や遠隔の説明ページのみへ隔離しない。自由割当・競合検出・初期化はアプリ用途に応じた個別要件であり、全UIへ無条件には要求しない。
- **設定の主表示は意味と現在値**：ラベル・現在値・変更結果を簡潔に配置する。長い定常的説明よりも、必要時に開ける対象近傍のⓘ／展開ヘルプ等を検討する。単一項目の説明に大きな画面遷移を要求しない。
- **ヘルプは説明責任の代替ではなく補助**：ヘルプを開かなくても主要操作の意味が概ね伝わる名称・階層・配置を先に整える。危険・必須条件・現在のエラーや失敗理由は必要な時点で明示する。
- **比較・編集の継続性**：値を変えながら結果を見るタスクでは、変更対象と結果を同時に認識できる構成を採用する。説明表示・キーボード表示・画面遷移後も対象と位置を保持する。
- **初見と熟練の両立**：発見可能な普通の操作経路と、頻繁な操作の高速経路を両立させる。ポインターホバーだけの説明に頼らず、対象端末・支援技術で利用可能な形を選ぶ。

### 小2視点の画面設計への適用

上位の「小2でも使いやすいか？」（USABILITY_POLICY の UX-00）を、**難しい機能を削るのでなく、入り口を明快にする**規則として適用する。

- **見れば分かる**：主対象・主操作・現在状態・次の行動を、説明文に頼らず名称、配置、既知の操作表現で示す。
- **触れば変わる**：押す、選ぶ、動かす等の操作と対象の変化を対応付け、操作が受理されたか分かる反応を示す。
- **試せば結果が見える**：安全に試せる変更は、変更中に結果を比較・確認できる構造を優先する。外部送信・不可逆処理は例外として明示する。
- **間違えても戻せる**：Cancel／Undo／Restore等の適切な経路を設け、操作中の文脈と入力を保持する。
- **簡単な操作の組合せ**：少数の一貫した操作規則を再利用し、高度な機能は必要に応じ段階的に見せる。専門機能の精度・表現力・既存利用者の効率を犠牲にしない。

検収では「長文説明を読まずとも何から始めるか分かるか」「結果がすぐに見えるか」「試行が危険なくできるか」「間違いを直せるか」を主要タスク単位で確認する。

### 構造からの再設計と非加算型改善

利用者の目的を達成するための**認知単位（対象・行為・結果）**を先に構成する。現行のタブ、設定画面、モーダル、説明文、既存コンポーネントは再利用候補であり、必須の画面骨格とみなさない。

- 不便の根本原因が画面分割、選択状態、階層、操作順序にある場合、局所的なボタン・ヘルプ・チェック追加で埋め合わせず、構造変更を検討する。
- **見て理解 → 試す → 結果が分かる → 戻せる**一連の体験が、不要な記憶、遠隔参照、再入力、画面往復なしに成立するよう、操作対象と結果の関係を設計する。
- まず「削除できる判断」「統合できる操作」「直接触れる対象」「自動で継承できる状態」を検討する。ただし必要な選択肢、専門機能、熟練者向け経路は削らない。
- 既存UIと異なる構造案を必要に応じ比較する。原初の要求、不確実な認知仮説、操作成功、反復負荷、回復可能性、実装・保守負担で選び、見た目や論理上の整合だけで決めない。
- 必要な認知負担を減らすことと、情報量や操作ボタンを機械的に減らすことは異なる。説明や追加機能が必要な場合も、全体の負担が減るかを基準にする。

## レイアウトとインタラクション
- テーブルは万能ではないことを認識し、複雑な関係や階層は適切な構造で表現する。
- システムが把握している情報を画面上で再利用できる構造にし、具体的な再入力削減・文脈継承の規則は `USABILITY_POLICY.md` を参照する。
- データ変化は、低リスクで予測可能な場合は自動反映を検討する。確認、競合解決、外部送信、コストを伴う処理では、状態と適用操作を明確にする。

## 挙動
- 軽い編集はインライン又はコンテキスト内を優先する。複雑な入力、検証、集中作業、アクセシビリティ上の理由がある場合は、別画面、フォーム、side panelを使い分ける。
- 変更の反映方法と回復手段を、操作の影響と非同期性に応じて示す。即時反映する場合は取り消し又は復元手段を検討する。
- 無効入力時は、理由と修正方法を示す。自動補正又はフォールバックは、ユーザーの意図を損なわず安全に行える場合に限る。
- 変更箇所を強調し、ユーザーの位置を維持し、隠れたスクロールバーや予期しない再配置を避ける。
- 汎用的なプレースホルダよりもドメインに合わせた適切なデフォルト値や候補を提示する。
- 一般的な記号やラベルなど、広く理解されているアイコンや表現を用いる。
