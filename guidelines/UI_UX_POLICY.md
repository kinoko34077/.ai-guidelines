# UI / UX ポリシー

## 設計原則
- 操作効率、標準操作慣習、状態・文脈継承、回復可能性、暗黙の操作期待の正本は `USABILITY_POLICY.md` とする。UI/UX側では、それらを画面構造・視覚階層・状態表示へ反映する。
- データベースのテーブルや内部変数名など実装の複雑さをユーザーに見せず、UIはユーザーの意図やドメイン概念を反映する。
- 内容を減らすのではなく、ユーザーが覚えたり比較したり検索したり保持したりする負担を減らす。
- 関係や階層を構造で示す。比較、一覧、入力に適する場合はテーブルやフォームを使い、直接操作は対象・安全性・実装環境に適する場合に優先する。
- UIは情報閲覧だけでなく、対象ユーザーの仕事を進めるための道具として設計する。CRUD管理画面が目的に適する場合まで排除しない。
- 編集や操作時には即時の視覚フィードバックを行い、外部トリガーが必要な場合は明示的に配置する。
- 編集中の対象を明確にし、選択中の項目を強調し、操作部の位置を一貫させる。
- 編集頻度、破壊性、実装可能性に応じて、Undo/Redo、復元、確認、履歴のいずれかを用意し、回復手段を明確にする。
- 参照切れや無効状態のデータは自動削除せず、問題を視覚的に示し、修復手段を提供する。
- PC用とモバイル用のUIを別々に設計し、単純に縮小しない。
- レイアウトやタイポグラフィ、色についてデザイントークンを用い、一貫性を保つ。
- 状態変化や作用範囲、関係を説明文に頼らず、視覚的に把握できるようにする。
- 不要な多方向スクロール、ネストされたスクロール領域、隠れた状態を避ける。主作業が複数領域を必要とする場合は、各領域の役割と現在位置を明確にする。
- タグは分類用途にのみ用い、エンティティの属性そのものをタグへ押し込まない。
- 編集・閲覧・デフォルトなど複数の状態を簡単に切り替えられるようにし、別画面への遷移を必要最小限にする。

## レイアウトとインタラクション
- テーブルは万能ではないことを認識し、複雑な関係や階層は適切な構造で表現する。
- システムが把握している情報を画面上で再利用できる構造にし、具体的な再入力削減・文脈継承の規則は `USABILITY_POLICY.md` を参照する。
- データ変化は、低リスクで予測可能な場合は自動反映を検討する。確認、競合解決、外部送信、コストを伴う処理では、状態と適用操作を明確にする。

## 挙動
- 軽い編集はインライン又はコンテキスト内を優先する。複雑な入力、検証、集中作業、アクセシビリティ上の理由がある場合は、別画面、フォーム、side panelを使い分ける。
- 変更の反映方法と回復手段を、操作の影響と非同期性に応じて示す。即時反映する場合は取り消し又は復元手段を検討する。
- 無効入力時は、理由と修正方法を示す。自動補正又はフォールバックは、ユーザーの意図を損なわず安全に行える場合に限る。
- 変更箇所を強調し、ユーザーの位置を維持し、隠れたスクロールバーや予期しない再配置を避ける。
- 汎用的なプレースホルダよりもドメインに合わせた適切なデフォルト値や候補を提示する。
- 一般的な記号やラベルなど、広く理解されているアイコンや表現を用いる。
