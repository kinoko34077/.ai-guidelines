# Usability Policy

## 目的

ユーザビリティは、UI部品や機能の存在ではなく、対象ユーザーが利用文脈の中で目的を正確・効率的・予測可能・安全に達成できるかで評価する。特に、明示されていなくてもユーザーが当然期待する操作を、設計・実装・検収の要求源として扱う。

## 上位原則

- ユーザーの目的を部品単位の実装より優先する。
- OS、プラットフォーム、一般的なGUI、同種アプリで定着した操作慣習を合理的な理由なく壊さない。
- システムが既に知っている値、選択、位置、検索条件、対象を再入力・再探索させない。
- 同じ目的に自然な複数の入力・操作経路がある場合、対象タスクに必要な代替経路を検討する。
- 現在の状態・文脈・位置を、画面遷移、再描画、再実行、ダイアログ表示だけを理由に失わせない。
- 誤操作、失敗、中断から、入力や作業状態を保って戻れるようにする。必要に応じて Undo / Retry / Cancel / Restore を用いる。
- 操作結果、処理状態、作用範囲、保存状態を認識可能にする。
- 「要求されていない」は単独の除外理由にしない。ただし、利益、誤操作、複雑性、保守負担、仕様・安全境界を比較して採否を決める。

## 利用者起点の定義と設計責務

**思いやりを設計責務として扱う。** ここでの思いやりとは、利用者の目的・期待操作・利用環境・認知負担・不安・制約を、明示要求の前から想定し、それらを軽減する設計・実装・検証上の責任を指す。開発者やAIの善意・自己評価ではなく、観測可能な利用体験によって評価する。

**要求された機能が動くことは、利用者にとっての完成と同義ではない。** 明示されていないからという理由で、対象環境で自然に期待される操作、発見経路、説明、回復手段を検討から除外しない。実装済み機能に加え、**未実装の当然期待される操作**を積極的に探索する。

### 全開発共通の「小2でも使いやすいか？」基準（UX-00）

**今後のすべての開発で、小学2年生でも使いやすいかを基本要件・設計時の問いとして扱う。** 特に利用者に接する画面、操作、設定、CLI、API等の入口では、初めて触れる利用者が本来不要な専門用語の暗記や長文説明なしに、基本目的と次の操作を理解できるかを検討する。

この基準の背景は、難しい・面倒・結果が見えない操作では、利用者、とりわけ子どもは容易に離脱するという設計上の仮説である。**小2視点は、表面的に幼い見た目へ変えることではなく、操作の本質的な単純さ・直感性・明瞭さを要求する。** Minecraftのような、簡単な基本操作の組合せで多様な創作へ到達できる体験を設計上の比喩とする。

**五つの判断原則**

1. **見れば分かる。** 説明書を探さず、何をどこでできるかが分かる。
2. **触れば変わる。** 操作すると対象が予測可能に反応し、状態の変化が分かる。
3. **試せば結果が見える。** 小さく安全に試せて、結果や効果をその場で確認できる。
4. **間違えても戻せる。** 誤操作・失敗・中断から、合理的に復帰できる。
5. **難しいことは、簡単な操作の組合せで実現できる。** 高度な機能を削らず、単純で一貫した基本操作を組み合わせて複雑な結果へ到達できる。

**適用と検証の境界**

- 全開発への共通要求とは、すべてのプロジェクトでこの観点を評価することである。GUI以外も、エントリーポイント、CLI/API利用経路、デフォルト、エラー、手順、ドキュメントを対象用途に即して整理する。
- 小学2年生が高度な専門知識、資格、業務権限、楽理、プログラミング言語、機密情報を習得せずに全操作できると主張するものではない。**本来必要な専門知識**と**UI/操作設計が不必要に要求している知識・手間**を分ける。
- 機能削減、過剰な誘導、危険操作の無条件即時実行、認証・安全・年齢制限の緩和を、この理念で正当化しない。基本操作の容易さと高度な機能・安全境界は両立させる。
- 児童による実使用が検証されたとは推定しない。「小2視点」は具体的な検収シナリオへ落とし込み、実際のユーザーテストを行っていない場合はその境界を明記する。

### 本質的・抜本的改善の原則（ゼロベースと水平思考）

**「小2でも使いやすいか？」は到達品質の基準であり、チェック項目・説明・機能の加算は改善そのものではない。** 既存UIが分かりにくいとき、現行の画面構造や内部実装を固定したまま修繕案を足すことを既定としない。人間の認知、利用者の目的、行為と結果の対応から、より少ない判断・移動・記憶で成立する構造を再構成する。

1. **原初の要件を不変条件として保持する。** 利用目的、確定機能、データの意味、保存・状態・安全・権限・互換性等を先に抽出する。ゼロベースとは、既存の配置・画面分割・操作順序や実装都合を自由に再検討することであり、ユーザーが指定した要求を白紙にすることではない。
2. **原因から解く。** 利用者の迷い・手戻り・誤操作・冗長手順を観察し、表面的症状と発生原因を分離する。利用者の認知負担・予測可能性・作業記憶・情報の近さ・フィードバックを因果仮説として扱う。
3. **水平思考で構造の異なる解を検討する。** ボタン追加・説明追記だけでなく、削除、統合、直接操作、配置・順序の変更、状態の再設計、適切な自動化、操作体系の組み換えを候補にする。形式的に複数案を増やさず、意味の異なる合理的な候補を選ぶ。
4. **論理だけで正解と断定しない。** 規約への適合や理論上の手数削減が、実際の分かりやすさを保証するわけではない。案ごとの予測を利用シナリオ、プロトタイプ、実操作によって検証し、反証・修正可能にする。
5. **総複雑性を減らす。** 機能・チェック・分岐・説明を増やした結果、利用者の判断負担や開発・保守の煩雑さが増していないかを評価する。必要十分な証拠を選び、チェックリスト自体も肥大化させない。
6. **原初の要件に照らして回帰確認する。** 単純化によって重要な機能、表現力、アクセシビリティ、熟練者の効率、安全性や回復手段を欠落させない。変更した構造と保持すべき要求の対応を確認する。

**優先順位：利用者の目的と原初要件 → 人間の認知に適合する操作体系 → 必要なUI部品・実装。** 不足した機能を足すのか、既存構造を減らして置き換えるのかは、この順序で判断する。

### 適用と権限の境界

- **三層で判断する**：共通ユーザビリティ原則、OS・端末・入力方式・用途の慣習、各製品の確定した操作契約。PC標準をモバイルへ無条件に転用しない。
- **標準の検討と無許可の機能追加は別**：必要性を導出しても、製品仕様、実装範囲、安全・公開・破壊操作の承認境界を越えない。標準要件の補完ではない大幅な機能追加は、個別要求へ分離する。
- **一律のコントロール追加を目的化しない**：ショートカットの自由割当、ⓘ、ツールチップ、ドラッグ操作等は対象タスクへの有効性と適合性で採否を決める。ショートカットの存在／操作地点での割当表示／ユーザーによる割当変更は別の要件として判定する。
- **安全・必須の説明は隠さない**：段階的開示のために危険、入力条件、エラーや不可逆な影響を見えなくしない。ヘルプはタッチ操作・支援技術で利用できる経路も考慮する。
- **推測と実証を分ける**：期待操作の推定は設計仮説として扱い、リスクや重要度に応じて実利用経路で検証する。静的実装やAI自身の「使いやすい」は操作成立の証拠にしない。
- **受入を要件別に管理する**：適用する各軸について PASS / FAIL / UNVERIFIED / N/A（理由付き）を区別する。未確認を完了へ読み替えない。

## 適用範囲

具体的な操作経路と検収項目は `uiux_vibecoding_protocol_pack_v1/07_USABILITY_BASELINE.md` に置く。対象作業に関係する場合だけ参照し、すべての操作を一律必須にしない。

実装前は、ユーザーが当然試す操作、継承できる状態、自然な代替経路、必要な回復手段、OS・プラットフォーム慣習を整理する。実装後は、実装した機能だけでなく、自然な操作の欠落を検収する。
