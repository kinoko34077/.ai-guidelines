# 08_REVIEW_CHECKLIST: UI検収チェックリスト

## 1. 情報設計
- 画面目的は1文で説明できるか。
- 主タスクは3〜5個に収まっているか。
- ユーザーが目的を正確・効率的・予測可能・安全に達成できるかを、対象タスクの利用文脈で説明できるか。
- High/Medium/Lowの情報優先度が見た目に反映されているか。
- 主データよりボタンや装飾が目立っていないか。

## 2. 操作階層
- Primary Actionは原則1つか。
- Secondary/Tertiary/Row/Dangerが分離されているか。
- 同じ強さのボタンが横並びで3つ以上ないか。
- 行操作がグローバル操作のように見えていないか。
- 危険操作が通常操作の隣にないか。

## 3. 文言・アイコン
- 長文ボタンが常時表示されていないか。
- 「〜する」の冗長語尾を短語化できないか。
- icon-onlyにtooltipとaria-labelがあるか。
- 逆に、意味が伝わらないアイコンだけになっていないか。
- 説明文はhelper/tooltip/empty stateへ分離されているか。

## 4. レイアウト
- 上部、左、中央、右、行末の役割が混ざっていないか。
- カードUIが一覧性や比較性を壊していないか。
- サイドバーや右パネルが主作業領域を狭めすぎていないか。
- toolbarが二段折返しやボタン密集になっていないか。
- 狭幅時の退避先があるか。

## 5. フォーム
- inputにvisible labelがあるか。
- placeholderに意味を依存していないか。
- errorが具体的で回復可能か。
- 保存/キャンセル/削除の配置と強さが適切か。

## 6. 標準操作・文脈継承
- この画面を初見で操作するユーザーが「当然できる」と試しそうな操作を列挙したか。
- 実装された要素だけでなく、未実装の自然な操作経路を確認したか。
- ファイル/フォルダ入力で `入力 / paste / 参照 / D&D / 現在値から参照開始` を検討したか。
- 参照ダイアログ、カレンダー、色選択、保存先などが現在値・選択中項目・前回状態から開始されるか。
- Enter、Esc、Ctrl/Cmd+C/V/A/Z、ダブルクリックなどが対象に自然な場合に期待通り動くか。
- D&D可能領域が視覚的に反応し、失敗時に理由を示すか。
- 自然だが非対応にした操作がある場合、非対応理由が明記されているか。

## 7. 欠落操作と回復性
- 実装した機能だけでなく、初見ユーザーが当然試す操作を列挙したか。
- OS・ブラウザ・同種アプリの慣習に反する操作を、合理的理由なく導入していないか。
- 既知の値、選択、検索条件、スクロール、開始位置などを不要に失っていないか。
- 状態、作用範囲、処理結果が認識できるか。成功・処理中・失敗・取消を混同していないか。
- 誤操作、入力エラー、非同期失敗、中断から、入力や作業状態を保って復帰できるか。
- 対象に自然な入力モダリティや代替経路を省いた場合、理由と代替手段があるか。
- 実環境で確認できない項目は、推測でOKにせず未確認理由を記録したか。

## 7.1 利用者起点・発見可能性・文脈内ヘルプの独立確認

\`guidelines/USABILITY_POLICY.md\` の UX-01〜UX-16 に従い、対象タスクに関係する項目を確認する。

### 利用者の目的と欠落操作
- 主要タスクの開始から完了までを、実装コンポーネントの存在とは独立に追跡したか。
- 利用者が当然試しそうなのに **実装されていない操作** を列挙し、適用・例外・別要求を判断したか。
- 初回、反復、誤操作、中断復帰のうち対象に必要なシナリオを検証したか。

### 操作の発見可能性
- 主要操作の入口を、操作経験のない利用者が対象から発見できるか。
- ショートカットは **実行可否／操作地点での割当表示／利用者による変更可否（必要な用途のみ）** を別々に判定したか。
- 隠れたジェスチャー・アイコンだけに依存した唯一の必須操作経路がないか。
- ショートカットを使わない操作経路が保たれているか。

### 情報とヘルプの配置
- 高頻度の操作領域が、冗長な常設説明で埋まっていないか。
- 設定の意味やショートカットを対象操作の近傍で確認できるか。
- ⓘ等の文脈内ヘルプは、現在の作業を失わずに開閉できるか。
- ヘルプを開かなくても主要操作の意味を理解できるか。
- 危険、必須条件、現行エラーを隠していないか。
- タッチ／支援技術で説明への到達経路があるか。

### 判定証拠
- 観測可能な実行時の主張を、操作テスト・実機等の妥当な経路で確認したか。
- 項目ごとの \`PASS / FAIL / UNVERIFIED / N/A\` を区別し、未検証を合格と扱っていないか。

## 8. 検証証拠と自動監査
- UI・Web・ブラウザ挙動について、機械的に観測・計測できる項目は、利用可能な自動操作・DevTools・CDP・DOM・Performance API・Accessibility Tree・ログ・ネットワーク計測等を使ってAI/実装者自身が確認したか。
- `F12を開いて値を教えてください`、`実際に触って問題ないか確認してください`等、機械取得可能な確認を利用者へ委譲していないか。
- runtime上の主張（滑らかさ、focus保持、selection保持、再描画、scroll位置、layout shift、通信時間、処理時間等）を、静的コードやscreenshotだけで済ませず、対象性質に合った実行時証拠で確認したか。
- screenshotは視覚証拠として補助利用し、性能・操作文脈保持・非同期挙動の唯一の根拠にしていないか。
- viewport依存の主張は、必要に応じて実viewport又はbrowser device metrics等で確認したか。
- accessibilityについて、role/name/state/live-region等の機械確認可能なsemantic情報を確認したか。
- Accessibility Treeの確認だけで実際のscreen reader読み上げ結果まで検証済みと誤認していないか。
- 検証結果に、対象SHA/version、実行経路、browser/環境、測定値又は観測状態、基準がある場合はthreshold、判定を残したか。
- projectにthresholdが存在しない値へ恣意的な合否基準を作らず、生値・比較対象・傾向として記録したか。
- 機械検証で成立しない残存境界がある場合、その範囲を具体的に限定し、周辺の機械検証可能事項までまとめて「人間確認」としていないか。
- review回答は、単なる「問題なさそう」ではなく、確認した証拠と `PASS / WARN / FAIL` 又はproject既定の同等判定を示しているか。

### 8.1 機能PASSとUX受入の区別

機能テストやビルドがPASSでも、利用者の目的達成、操作の発見、説明の配置、文脈維持、回復可能性が未検証なら、UI/UX受入全体をPASSとしない。プロジェクトで別の判定語彙がある場合は意味を対応づける。適用外は環境・用途に基づく根拠を記録し、理由のないN/Aで欠落を隠さない。

## 9. 最終判定
|判定|条件|
|---|---|
|OK|重大違反なし。小修正のみ|
|要修正|主操作、密度、文言、配置、標準操作、アクセシビリティ、検証証拠のどれかに明確な問題あり|
|差戻し|画面目的やレイアウト骨格から不適切|

